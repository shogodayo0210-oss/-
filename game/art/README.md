# アート指針

キャラクターの絵の作り方を決める。**数字と見た目を紐づける**のが方針の中心で、
「見ただけで何をするユニットか分かる」状態を目指す。

**v0.6での変更**：ドット絵限定の規約をやめ、平塗り〜セルシェードの2Dイラスト
（にゃんこ大戦争ぐらいの塗りの情報量）を正式な方向にした。理由と、
組み込みのために必ず守る条件は1章と7章にまとめてある。

## 0. 何を参照して、何を採らないか

| 参照 | 採るもの | 採らないもの |
| --- | --- | --- |
| **ドラゴンクエスト** | **系統でシルエットを共有する。** スライム系は丸い、ドラゴン系は翼 ―― 新キャラでも一目で系統が分かる。これを `race`（王国軍/動物/探検家/古代兵器/悪の組織）でやる | 正面向きの立ち絵。こちらは横スクロールなので側面固定 |
| **にゃんこ大戦争** | **横向き固定・楕円の影1枚・シルエット優先。誇張されたプロポーション。** 30体が同時に並んでも役割が読める作り | 正面シンボル的な構図。戦闘中は側面しか見えない |
| **ポケモン** | **役割が色で分かること。** タイプが色で伝わるのと同じで、アクセント色に役割を持たせる | 正面シンボル的な構図。戦闘中は側面しか見えない |

**共通して採るのは1つ。** 3作とも、**小さく表示しても「それが何か」が分かる**。
シルエットが第一で、描き込みは二番目 ―― これは塗りの情報量が上がった
いまも変わらない優先順位。

## 1. 解像度と組み込みの条件

**元絵の解像度はここでは縛らない。** エンジン側（`game/play/view.py` の
`UNIT_TARGET_H`/`AVATAR_TARGET_H`、`game/web/view.js` も同じ値）が、
読み込んだ絵の実寸に関わらず**画面上の高さ**を正規化して表示する。

| 対象 | 画面上の高さ | 画面での扱い |
| --- | ---: | --- |
| ユニット | **96px** | 画面高さのおよそ 1/6（旧・48pxドット絵を2倍表示していたのと同じ大きさ） |
| 拠点（アバター） | **128px** | レーンの両端 |

1レーンは 240m を画面幅に収めて描く。**同時に最大20体**が並び
（`max_units_per_side`）、**味方どうしは重なる**ので、密集したところでは
シルエットが前後に重なる。この密度で潰れないことが条件 ―― ここは
解像度を変えても変わらない。

### 組み込みの条件（絶対に守ること）

実際に生成した絵をエンジンに読み込ませて分かった、技術的な必須条件。

1. **背景は完全透過（アルファチャンネルあり）。** 白背景・単色背景は不可。
   エンジンは透明でないピクセルの範囲でキャラの実体位置（体力バーの
   高さなど）を判定するため、背景が不透明だと表示位置がずれる。
2. **1ファイル＝1ポーズ。** タイトル文字・コマ番号・説明文・効果線などを
   絵そのものに焼き込まない。複数ポーズを1枚のシートに合成しない。
3. **同じキャラの複数コマ（アニメーション）は、キャンバスサイズと
   足元の接地位置をコマ間で揃える。** ここがずれると、コマ送りした
   ときにキャラ全体が横にガクッとずれて見える。
4. **キャラは画面の右を向いた状態で統一する。** 左向きはエンジンが
   自動で左右反転して作るので、右向きの絵だけでよい。

**「細かめ」の基準**：小さく縮小されても種族の記号（2章）と役割の
シルエット（3章）が判別できる粒度。塗りの情報量を上げすぎて、
96px表示時にディテールが潰れて意味を持たなくなるものは避ける ――
実際に `--capture` で書き出して確認する（7章）。

## 2. 配色

**種族ごとに色相と形の記号を固定する。**

| 種族 | 方向 | 形の記号 |
| --- | --- | --- |
| 王国軍 | 青灰 ＋ 金 | 目深の兜、直線的な武具、左肩の紋章 |
| 動物 | 茶 ＋ 橙 | 耳と尾、裸足、首の布 |
| 探検家 | 土色 ＋ 青緑 | つば広の帽子、背嚢、ロープとランタン |
| 古代兵器 | 灰 ＋ 水色 | 角張った胴、継ぎ目、光る動力線、面で顔が無い |
| 悪の組織 | 紫 ＋ 緑 | ほつれた裾、光る目、仮面か頭巾 |

**`race` は見た目だけの区分ではない。** 特性（同胞・連携）が種族を見るので、
編成の材料になる（設計書2.9・2.10）。だから**遠くから一目で分かる**必要がある ――
色相だけでなく、形の記号も種族ごとに固定する。

`palette.json` の6色1組（輪郭・影・本体・光・アクセント・アクセントの影）は
**手続き生成の仮絵（`game/tools/sprites.py`）が使う内部形式**。本番の絵を
描く・生成するときの絶対の制約ではないが、種族ごとの色相の目安として
そのまま使える。

## 3. シルエットの規約

**数字がそのまま形になる。** ここが指針の核心で、塗りの情報量が
上がっても変わらない。

| データ | 見た目 |
| --- | --- |
| 対拠点倍率 ≤ 0.6（＝壁） | **横に広く低い。前に盾**を構える |
| 攻撃範囲の手前 > 0（＝遠方範囲） | **上を向いた砲身。** 死角があることが形で分かる |
| 攻撃範囲の奥 > 42（＝遠距離） | **細く高い。得物が長い**（長さは射程に比例。最長は80m） |
| 貫通 ≥ 2（＝範囲攻撃） | **刃・爆風・火が横に広がる。** 単体は点で当たる形 |
| 移動速度が中央値超え | **前傾。** 重心が前足に乗る |
| コストが高い | **大きい。** キャンバスを埋める |
| コストが上位4割かつ近接（＝大型） | **胴が太い。** 遠距離の細さと対になる |
| 対拠点倍率 ≥ 1.3 | **背中に攻城具**を背負う |
| 対壁倍率 > 1.5 | **刃が厚い**（壁を割る道具に見せる） |
| ノックバック 1 | **踏ん張る。** 後退しないことが姿勢で分かる |
| ノックバック 4 | **装甲が薄い。** 押し戻される軽さ |

**なぜ紐づけるか。** 初見の人が「見ただけで何をするユニットか」を当てられるように
するため。ドラクエもにゃんこもポケモンも、ここが強い。
ルールブックを読ませる前に、**絵が役割を説明する**状態を作る。

この規約は文章だけでなく、`game/tools/sprites.py` が**実際にこの通り描く**
（いまの仮絵の生成器。7章）。

そして `game/tools/art_brief.py` が、この規約と `art/looks.json`（数字から
決まらない見た目 ―― 何を着ていて何を持っているか、世界観・性格）を合わせて
**[`BRIEF.md`](BRIEF.md) を書き出す**。1体ぶんがそのまま生成AIに貼れる依頼文に
なっているので、外注も生成も同じ紙を見ることになる。

```console
$ python3 game/tools/art_brief.py            # art/BRIEF.md を作り直す
$ python3 game/tools/art_brief.py --id oni   # 1体だけ標準出力に
```

**数字を動かしたら生成し直す。** 依頼書に数字を書き写さないのは、
DPS を data に持たせないのと同じ理由 ―― 両方に書くと必ずどちらかがズレる。

## 4. アニメーション

| 動作 | 枚数 | 備考 |
| --- | ---: | --- |
| 待機 | 2 | 呼吸。ループ |
| 歩行 | 4 | ループ |
| 攻撃 | **4** | 配分を `attack_windup_sec` に一致させる（下記） |
| 被弾 | 1 | 色を明るく飛ばすだけでもよい |
| 退場 | 2 | |
| **計** | **13枚** | 1体あたり |

**いまエンジンが読み込むのは、1体につき静止1枚（待機ポーズ）だけ。**
`game/play/view.py` はユニットごとに `game/art/out/units/{id}.png` を
1枚だけ読む。歩行・攻撃・被弾・退場のコマ送りをコードから読む仕組みは
まだ実装していない ―― 下の配分表・接地位置の条件は、その機能が入った
ときにそのまま使うためのもの。いま作る絵は無駄にはならない。

### 攻撃アニメの配分が肝

**振りかぶりの長さを、データの `attack_windup_sec` に一致させる。**

| ユニット | 発生 | 振りかぶり | 当たり | 戻り |
| --- | ---: | ---: | ---: | ---: |
| 臼砲 | 0.80秒 | 3枚 | 1枚 | ―― |
| 砲手 | 0.70秒 | 3枚 | 1枚 | ―― |
| 双剣 | 0.10秒 | 1枚（ほぼ無し） | 1枚 | 2枚 |
| 兵卒 | 0.15秒 | 1枚 | 1枚 | 2枚 |

**ここがずれると、見切りの読み合いが嘘になる。**
設計書7.5で「大きい一撃は必ず発生0.6秒以上」と決めたのは、
*振り始めが見えたら反応できる*ようにするため。
絵が先に当たったり、逆に振りかぶりが見えないと、その約束が破れる。

**カードの詠唱も同じ**。0.5〜0.9秒の詠唱には、足元のサークルが
その秒数をかけて広がる演出を当てる。見切り（0.3秒）を合わせる相手がこれ。

**複数コマを作るときは、1章の組み込みの条件（接地位置を揃える）を必ず守る。**
守らないと、コマ送りしたときにキャラが横にずれて見える。

## 5. 拠点（アバター）

アバターは**殴られる当事者**なので、**城と人が一体**になった絵にする。
画面端に立っているだけの飾りではない。

見た目の方向づけ（`look`）は6種。数字には影響しない。

| look | 飾り | 該当アバター |
| --- | --- | --- |
| **可憐** | リボン。淡い桃色 | 姫・獣使い |
| **剛力** | 角。赤茶と金 | 不動・豪傑 |
| **知性** | 尖り帽。青と水色 | 斥候・軍師・術師・職人・隠者 |
| **俊敏** | なびく布。緑と淡黄 | 疾風 |
| **怪異** | 仮面。紫と黄緑 | 賭博師 |
| **王道** | 王冠。金 | 統率 |

拠点HPが減るほど**塔が崩れる**（3段階）。「あとどれだけ削れば勝てるか」を
数字ではなく形で見せる。

## 6. 発注の単位

1体あたりの流れ：

```
data の数字（役割が決まっている）
  → ラフ（シルエットだけ。3章の規約に沿っているか確認）
  → 本番の絵（透過PNG、1ファイル＝1ポーズ、96px表示を想定した情報量）
  → アニメ13枚（1章の接地位置の条件を守る）
  → 音（攻撃・被弾・退場）
```

**物量の目安**

| | 数 | ×枚数 | 合計 |
| --- | ---: | ---: | ---: |
| ユニット | 32 | 13 | 416枚 |
| 切り札 | 3〜8 | 13 | 39〜104枚 |
| アバター（拠点） | 12 | 崩れ3段階 | 36枚 |
| カードのアイコン | 30 | 1 | 30枚 |
| エフェクト | 〜20 | 4〜8 | 80〜160枚 |

**ここがプロジェクトの物量の大半**になる。
数字と設計は先行しているが、絵は1枚も本番のものが無い。

## 7. いまの仮絵と、本番の絵の差し込み方

### 手続き生成の仮絵（旧ドット絵）

`game/tools/sprites.py` が data から仮のドット絵を生成する（依存なし）。
**いまも動くが、1章で採用した方向とは絵柄が異なる**（3章のシルエット
規約だけは共通なので、仕様の実行できる形としては引き続き使う）。

```console
$ python3 game/tools/sprites.py
ユニット 32 / アバター 12 を game/art/out に書き出した
```

- `out/units_sheet.png` — 32体の一覧
- `out/avatars_sheet.png` — 12体の一覧
- `out/units/*.png`, `out/avatars/*.png` — 個別

目的は2つだけ。

1. 試遊版に**今すぐ何かを映せる**ようにする（絵待ちで開発を止めない）
2. 3章の規約を、文章ではなく**実行できる形**にしておく

### 本番の絵への差し替え（デスクトップ版）

`game/play/view.py` は `game/art/out/units/{id}.png` /
`game/art/out/avatars/{id}.png` を**ファイル名がユニットidと一致していれば
そのまま読む**（1章の組み込みの条件を満たしていること）。手続き生成の
出力と同じ場所なので、`sprites.py` を再実行すると上書きされる ――
本番の絵を置いたユニットは再実行の対象から外すか、置き場所を分けて
差し込む運用にすること（現状は運用でカバー。自動化はしていない）。

絵の解像度は問わない（1章）。エンジンが表示時に正規化する。

### Web版はまだ対応していない

**`game/web/out/index.html` は、いまのところ常に手続き生成の仮絵を
焼き込む。** `game/tools/build_web.py` の `art_bundle()` は
`game/tools/sprites.py` の生成器を直接呼んでいて、
`game/art/out/units/*.png` の実ファイルを読みに行く経路が無い。

本番の絵をWeb版でも使うには、`build_web.py` に「`game/art/out/units/{id}.png`
が存在すればそれを使う」という差し込み経路と、依存を増やさずに
（PNGのbboxを`zlib`/`struct`だけで読む）透過範囲を測る処理を足す必要がある。
**未実装 ―― 本番の絵が揃うタイミングで着手する。**
